# AI Employee Framework — Design & Implementation Plan

**Date:** 2026-04-14  
**Status:** Final (merged from two plans — UI-alignment additions incorporated)  
**Location:** Framework in `AgentFoundation`; concrete roles/employees in `OpenStartup`

---

## 1. Overview & Design Philosophy

### The Core Insight

An AI employee is created in two stages:

```
Stage 1: Role Creation (enterprise-generic)
  Phases 1+2 → AIEmployeeRole
    → /create-role  → role_document.md    (what this role does, across the org)
    → /role-setup   → SKILL.md files      (how it does it, with what tools)

Stage 2: Employee Instantiation (team-specific)
  Phase 3 → AIEmployee
    → /team-onboard → team_context.yaml   (where it works, with whom)
```

`AIEmployeeRole` is analogous to a **job description** — reusable, enterprise-generic, independent of any specific team.  
`AIEmployee` is analogous to a **hired person** — an instance of a role, deployed to a specific team, with its own identity and runtime state.

### Composition over Inheritance

`AIEmployee` holds a **reference** to `AIEmployeeRole` (composition), not inheritance in the class sense. This allows:
- An employee to change roles over time
- Multiple employees to share the same role definition
- Role updates to propagate to all employees of that role
- Clean serialization (role config stays in role folder; employee config stays in employee folder)

### File Format Decisions

| Artifact | Format | Rationale |
|---|---|---|
| Role/employee config | **YAML** | Human-readable, editable, supports multiline strings, standard for configs |
| Skill metadata | **YAML** | Config, not data |
| Tool registry | **YAML** | Config |
| BTA checkpoints | **JSON** | Machine-generated by existing BTA framework |
| Runtime state | **JSON** | Frequently updated, machine-written |
| Role/skill descriptions | **Markdown** | Prose for LLM injection (SKILL.md, role_document.md) |

## 3. Data Models (AgentFoundation)

### 3.1 Enumerations (`employees/models/enums.py`)

```python
from enum import StrEnum

class RoleStatus(StrEnum):
    draft = "draft"           # role document created, not yet set up
    active = "active"         # role_setup complete, ready to instantiate
    deprecated = "deprecated" # superseded by newer version

class EmployeeStatus(StrEnum):
    onboarding = "onboarding" # team-onboard in progress
    active = "active"         # fully operational
    idle = "idle"             # no current task
    blocked = "blocked"       # awaiting human decision
    away = "away"             # temporarily inactive
    retired = "retired"       # permanently deactivated

class AutonomyLevel(StrEnum):
    high = "high"     # can act independently
    medium = "medium" # needs approval for key actions
    low = "low"       # assists only, humans decide
```

### 3.2 UI Alignment — Existing Fixture Schema (Critical)

The OpenStartup UI already reads and renders `role_configs.json` and `agent_states.json`
via `RoleControlPopover.js` and `EmployeeCard.js`. The `AIEmployeeRole` model **must
round-trip to these formats** for the dashboard to work with real data.

`role_configs.json` structure (source of truth for UI):
```json
{
  "Program Manager": {
    "description": "...",
    "mindsets": [{"text": "...", "default_enabled": true}],
    "sops": [{"title": "...", "trigger": "...", "steps": ["..."]}],
    "communication": {"allow_all": true, "allowed_roles": [...], "blocked_roles": []},
    "guardrails": {
      "max_concurrent_tasks": 3, "max_autonomy": "medium",
      "escalation_threshold": "2h", "max_token_budget": "100K",
      "output_review": "on_errors", "approval_required": [...]
    }
  }
}
```

`agent_states.json` adds: `autonomy.can_auto_approve[]`, `autonomy.max_hours_without_checkin`.

Also note: `create_role/executor.py` uses `ROLE_SYNTHESIS_INSTRUCTIONS` defining an implicit
11-section role_document.md schema (Role Overview, Core Responsibilities, Skills & Competencies,
Tools & Integrations, SOPs, Guardrails, Metrics, etc.). The YAML models should align with
these sections so role_document.md can be parsed back into structured fields.

### 3.3 Skill & Tool Config (`employees/models/skill.py`)

```python
from dataclasses import dataclass, field
from pathlib import Path

@dataclass
class SkillConfig:
    id: str                    # e.g. "project_tracking"
    display_name: str
    skill_md_path: Path        # path to SKILL.md
    metadata_path: Path | None # path to skill.yaml (optional)
    description: str = ""      # short description (from skill.yaml or first line of SKILL.md)

@dataclass
class ToolConfig:
    enabled: list[str] = field(default_factory=list)   # tool names from tool registry
    disabled: list[str] = field(default_factory=list)  # explicit overrides
    
    @property
    def effective_tools(self) -> list[str]:
        return [t for t in self.enabled if t not in self.disabled]

@dataclass
class MindsetDirective:
    """Toggleable directive shaping how the agent approaches work.
    
    Maps directly to role_configs.json mindsets[] format.
    Runtime-toggled via RoleControlPopover.js.
    """
    text: str
    default_enabled: bool = True

@dataclass
class SOPDefinition:
    """Standard Operating Procedure with inline steps.
    
    Maps directly to role_configs.json sops[] format.
    Optional file ref for detailed Jinja2 SOP template.
    """
    title: str
    trigger: str = ""
    steps: list[str] = field(default_factory=list)
    file: str = ""  # optional: path to detailed SOP Jinja2 template

@dataclass
class CommunicationPolicy:
    """Inter-employee communication permissions.
    
    Maps directly to role_configs.json communication format.
    """
    allow_all: bool = True
    allowed_roles: list[str] = field(default_factory=list)
    blocked_roles: list[str] = field(default_factory=list)

@dataclass
class GuardrailConfig:
    """Operational guardrails defining autonomy boundaries.
    
    Merged from role_configs.json guardrails + agent_states.json autonomy sections.
    """
    # From role_configs.json guardrails
    max_autonomy_level: AutonomyLevel = AutonomyLevel.medium
    max_concurrent_tasks: int = 3
    escalation_threshold: str = "2h"        # e.g. "2h", "30m"
    max_token_budget: str = "100K"          # cost control
    output_review: str = "on_errors"        # always | on_errors | never
    approval_required: list[str] = field(default_factory=list)   # always need human approval
    
    # From agent_states.json autonomy
    can_auto_approve: list[str] = field(default_factory=list)    # no human approval needed
    max_hours_without_checkin: int = 8
    
    # Tool-level confirmation gates (SOP-driven)
    requires_confirmation: list[str] = field(default_factory=list)
    
    # Free-text guardrail statements (injected into system prompt)
    custom_rules: list[str] = field(default_factory=list)
```

### 3.3 AIEmployeeRole (`employees/models/role.py`)

```python
from __future__ import annotations
from dataclasses import dataclass, field
from datetime import datetime
from pathlib import Path

@dataclass
class AIEmployeeRole:
    """
    Generic, enterprise-aware AI employee role definition.
    
    Produced by Phases 1+2 (create_role + role_setup).
    Independent of any specific team — describes WHAT the role does
    and HOW it does it across the organization.
    
    Stored as: _data/roles/{role_id}/role.yaml
    """
    # Identity
    id: str                        # e.g. "program_manager"
    name: str                      # e.g. "Program Manager"
    description: str               # brief description for UI display
    version: str = "1.0"

    # Artifacts (produced by /create-role and /role-setup)
    role_document_path: Path | None = None   # path to role_document.md
    skills: list[SkillConfig] = field(default_factory=list)
    tools: ToolConfig = field(default_factory=ToolConfig)
    guardrails: GuardrailConfig = field(default_factory=GuardrailConfig)

    # UI-aligned fields (maps to role_configs.json — consumed by RoleControlPopover.js)
    mindsets: list[MindsetDirective] = field(default_factory=list)
    sops: list[SOPDefinition] = field(default_factory=list)
    communication: CommunicationPolicy = field(default_factory=CommunicationPolicy)

    # Lifecycle
    status: RoleStatus = RoleStatus.draft
    created_at: datetime = field(default_factory=datetime.utcnow)
    updated_at: datetime = field(default_factory=datetime.utcnow)
    created_by: str = ""          # session_id or user that ran /create-role

    # Metadata
    tags: list[str] = field(default_factory=list)
    notes: str = ""

    @property
    def is_ready(self) -> bool:
        """True if role_setup is complete and role can be instantiated."""
        return (
            self.status == RoleStatus.active
            and self.role_document_path is not None
            and len(self.skills) > 0
        )

    @classmethod
    def from_yaml(cls, path: Path) -> "AIEmployeeRole":
        """Load from role.yaml file."""
        ...

    def to_yaml(self, path: Path) -> None:
        """Save to role.yaml file."""
        ...

    def to_role_config(self) -> dict:
        """Convert to role_configs.json format for the dashboard UI.
        
        Enables AIEmployeeRole to replace fixture data in role_configs.json,
        making the UI serve real role data instead of mock fixtures.
        """
        return {
            "description": self.description,
            "mindsets": [{"text": m.text, "default_enabled": m.default_enabled}
                         for m in self.mindsets],
            "sops": [{"title": s.title, "trigger": s.trigger, "steps": s.steps}
                     for s in self.sops],
            "communication": {
                "allow_all": self.communication.allow_all,
                "allowed_roles": self.communication.allowed_roles,
                "blocked_roles": self.communication.blocked_roles,
            },
            "guardrails": {
                "max_concurrent_tasks": self.guardrails.max_concurrent_tasks,
                "max_autonomy": self.guardrails.max_autonomy_level.value,
                "escalation_threshold": self.guardrails.escalation_threshold,
                "max_token_budget": self.guardrails.max_token_budget,
                "output_review": self.guardrails.output_review,
                "approval_required": self.guardrails.approval_required,
            },
        }

    def to_employee_variable(self) -> dict:
        """Convert to .variables.yaml employee format for prompt injection.
        
        Enables AIEmployeeRole to populate the employee.mindset template variable,
        replacing the static .variables.yaml mindset dict.
        """
        return {
            "name": self.name,
            "role": self.description,
            "mindset": {m.text: m.text for m in self.mindsets if m.default_enabled},
        }
```

### 3.5 AIEmployee (`employees/models/employee.py`)

```python
@dataclass
class AIEmployee:
    """
    Concrete AI employee instance — a role deployed to a specific team.
    
    Produced by Phase 3 (/team-onboard).
    Holds a reference to AIEmployeeRole (composition, not inheritance).
    
    Config stored as: _data/employees/{employee_id}/employee.yaml
    Runtime state: _data/employees/{employee_id}/state.json (gitignored)
    """
    # Identity
    id: str                        # e.g. "alice_pm"
    persona_name: str              # e.g. "Alice"
    display_name: str              # e.g. "Alice — Platform PM"

    # Role (composition)
    role_id: str                   # references AIEmployeeRole.id
    role: AIEmployeeRole | None = None  # loaded at runtime

    # Team deployment (Phase 3)
    team_context: TeamContext | None = None

    # Persona / communication
    greeting: str = ""             # "Hi, I'm Alice..."
    communication_style: str = "professional"

    # Lifecycle
    status: EmployeeStatus = EmployeeStatus.onboarding
    hired_at: datetime = field(default_factory=datetime.utcnow)
    retired_at: datetime | None = None

    # Runtime (NOT in YAML — stored in state.json)
    # current_task_id, metrics, task_queue, active_correspondence
    # are loaded separately via StateManager

    @property
    def effective_tools(self) -> list[str]:
        """Merge role tools with team-specific overrides."""
        if not self.role:
            return []
        base = set(self.role.tools.effective_tools)
        base.update(self.team_context.additional_tools if self.team_context else [])
        base.difference_update(self.team_context.disabled_tools if self.team_context else [])
        return sorted(base)

    @property
    def all_skills(self) -> list[SkillConfig]:
        """Role skills (team-specific additions can be added in Phase 3)."""
        return self.role.skills if self.role else []

    @classmethod
    def from_yaml(cls, path: Path, role_registry: "RoleRegistry") -> "AIEmployee":
        """Load employee.yaml and resolve role reference."""
        ...

    def to_yaml(self, path: Path) -> None:
        """Save employee.yaml (without runtime state)."""
        ...
```

## 7. Integration with OpenStartup Workflow

### How `/create-role` populates AIEmployeeRole

```
User: "hire a program manager"
    ↓ Phase 0: multiple_choice → role_function = "Coordinates & manages"
    ↓ Phase 1: LLM invokes /create-role
    ↓ ToolDispatcher → create_role.executor:execute()
    ↓ BTA research → writes role_document.md to working_dir
    ↓ execute() returns ToolExecutionResult with role_document_working_dir
    ↓ ConversationService._persist_workflow_updates() saves to session
    ↓ Phase 1b: LLM presents role document for review
    ↓ Manager approves → Phase 2
    ↓ LLM invokes /role-setup
    ↓ ToolDispatcher → role_setup.executor:execute()
    ↓ BTA research → writes SKILL.md files + tool configs
    ↓ POST-TOOL: RoleRegistry.register(AIEmployeeRole.from_artifacts(working_dir))
```

The last step — **materializing an `AIEmployeeRole` from BTA artifacts** — is the key integration point. After `/role-setup` completes, `execute()` should:
1. Read `role_document.md` and skill artifacts from `working_dir`
2. Create an `AIEmployeeRole` instance
3. Write `role.yaml` to `_data/roles/{role_id}/`
4. Register with `RoleRegistry`

### How `/team-onboard` creates AIEmployee

```
Phase 3: LLM collects team context (jira_projects, slack_channels, focus_areas)
    ↓ LLM invokes /team-onboard role_document_path team_name
    ↓ ToolDispatcher → team_onboard.executor:execute()
    ↓ Creates TeamContext from collected info
    ↓ Creates AIEmployee with role reference
    ↓ Writes employee.yaml + team_context.yaml to _data/employees/{id}/
    ↓ Initializes state.json with status=onboarding→active
    ↓ EmployeeRegistry.register(employee)
    ↓ Returns ToolExecutionResult confirming employee is live
```

## 10. Key Design Decisions (Summary)

| Decision | Choice | Rationale |
|---|---|---|
| Inheritance vs composition | **Composition** (`role: AIEmployeeRole` field) | Flexibility — employees can change roles; easier serialization |
| Python model library | **dataclasses** (not attrs/pydantic) | AF uses attrs internally but dataclasses are simpler for new domain models; Pydantic adds validation but is heavy |
| YAML library | **PyYAML** (already in deps) | Sufficient for config loading; add pydantic-yaml later if validation needed |
| Where framework lives | **AgentFoundation** | `AIEmployeeRole` + `AIEmployee` are generic — any project can use them |
| Where data lives | **OpenStartup/_data/** | Concrete roles/employees are project-specific |
| State vs config split | **YAML config + JSON state** | Config is stable and human-readable; state changes frequently and is machine-managed |
| `_data/` gitignored? | **No — `_data/` is version-controlled** | Role documents and employee configs are valuable artifacts worth tracking; only `state.json` and `_runtime/` are gitignored |
